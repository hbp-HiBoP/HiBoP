# T12 - Online site-filter job

## Objective

Keep `IsFiltered` as its own site-state field and add a canonical, generation-fenced online job for applying it across Desktop and Quest. Online evaluation runs on Desktop. Quest receives and atomically applies the resulting site mask, then acknowledges the exact applied generation.

There is currently no Quest UI button for filtering. T12 adds the request and response path so a future Quest UI can send a command without evaluating conditions on Quest while online.

## Agreed UI scope

This task covers the active Desktop paths only:

| Included entry point | Operation semantics |
| --- | --- |
| `HBP.UI.Toolbar.ToolbarExternalActions.DefaultOpenSiteFilters(Base3DScene)` opens `SiteFiltersWindow`; `SiteFiltersWindow.ApplyFilters()` | Apply the selected filter conditions to unmasked sites. Preserve the existing `IsFiltered` value for masked sites. |
| `HBP.UI.Toolbar.Site.SiteFilters` reset button, whose existing action is `SelectedScene.ResetSiteFilters()` / `Base3DScene.ResetSiteFilters(bool included = true)` | Reset every site to included, including masked sites. |
| `HBP.UI.Informations.InformationsWrapper.FilterChannels(ChannelStruct[])` | Clear the current filter over the full scene, then include sites matching `(Patient.ID, site.name)`. This has historically included masked sites. |

The following paths are excluded because they are disabled or unavailable to a normal user: `HBP.UI.Module3D.Sites.SitesInformations.OpenSiteFilters()`, the older Basic/Advanced site-condition window path, and its handwritten AdvancedConditions parser/string path. T12 does not add a Quest UI control.

`IsFiltered` remains distinct from `IsBlackListed`: the two fields can affect the same scientific visibility, but this job reads and writes only `IsFiltered`. The three included entry points retain their different target and reset semantics above.

## Online protocol and ownership

1. A filter request carries a job ID and a typed command for conditions, unmasked reset, full reset, or channel selection. The request snapshots selected conditions when accepted; condition payloads are limited to filter types registered for `Site` objects (including valid nested `All`/`Any` groups).
2. Desktop allocates a `Filter` generation and attempt, reserves the scene's sensitive-activity scope, and sends `Started` to Quest.
3. Desktop evaluates the prepared roster on its owning thread, yielding between bounded batches. A 200 ms delayed loading visual appears for long-running UI and remote jobs.
4. Desktop applies and publishes one canonical `SetSiteFilterResult` mutation containing the job ID, generation, stable roster hash, site count, and packed inclusion mask. Large results use the existing scene-operation bulk transfer.
5. Quest validates the active job generation and exact roster identity, atomically stages and applies the complete `IsFiltered` mask, and returns `Ready` only after the canonical mutation has been applied.
6. Desktop and Quest release their sensitive-activity scopes after terminal failure/cancellation or after the successful Quest apply acknowledgement. Quest loading cancellation sends a `Cancel` control for the exact active generation; a Quest `Failed` control invalidates Desktop's generation and cancels evaluation before the mask can be published.

Cancellation invalidates the Desktop generation before a result can publish. Quest drops results for a stale job and retires any abandoned partial transfer, then drains deferred scene records in order. A remote filter belongs to the published Quest session, not an individual transport connection: a transient disconnect preserves it during the existing reconnect grace, while confirmed `OfflineLocal` retires it. Reconnection does not automatically restart a cancelled request. The transport remains responsible for its normal connection recovery.

The current `IsFiltered` mask is included in the typed publication checkpoint, so a newly published Quest scene receives the settled state as well as subsequent live changes.

## Offline behavior on Quest

When Quest has entered confirmed `OfflineLocal`, it checks the request against the prepared local scene and roster before evaluation. Reset and channel-selection requests need no external condition resources. Offline conditions are limited to `Name`, `PatientName`, `Attributes`, `RawSitePosition`, site or patient `SiteTag`, `Activity` when local site statistics are complete, and `SpecificSiteLocation` in `RegionOfInterest` mode; these may be nested in valid `All`/`Any` groups. Tag definitions must resolve from the scene or local tag catalog, and site/patient tag collections must be present for each unmasked site that will be evaluated. MRI-mask files, atlases, mesh/cut-plane geometry, and condition types that do not operate on a site are rejected before changing `IsFiltered`.

While online, Quest does not evaluate conditions locally: it sends the typed command to Desktop. No automatic offline retry is performed after a cancelled online request.

## Out of scope

- Quest-side online condition evaluation.
- Adding or enabling a Quest filtering button.
- Re-enabling the disabled Basic/Advanced UI or handwritten AdvancedConditions parser.
- Automatically replaying a cancelled job after a connection transition.

## Acceptance criteria

- A1. Sync runtime, Sync scene, Quest runtime, and UI assemblies compile.
- A2. Desktop is the only online evaluator; Quest applies the exact canonical roster mask and acknowledges only after successful application.
- A3. Cancellation and generation fencing prevent an A result or partial transfer from overwriting a later B result.
- A4. The filter mask survives typed checkpoint encode/decode and applies without an echo proposal.
- A5. The three included Desktop entry points use T12 while preserving their separate site-target semantics.
- A6. Quest offline execution is gated before state changes and rejects unsupported condition/resource requirements cleanly.

## Reviewer notes

- The canonical field is `IsFiltered`; T12 does not merge it with `IsBlackListed`.
- The Site Filters window filters unmasked sites only. Its reset leaves masked sites unchanged.
- Toolbar reset includes masked sites. `FilterChannels` replaces the mask for all sites, including masked sites.
- `SitesInformations.OpenSiteFilters()` and Basic/Advanced are deliberately outside the current user-accessible UI scope.
- Desktop local UI and future Quest commands converge on the same Desktop job/result protocol when online.
