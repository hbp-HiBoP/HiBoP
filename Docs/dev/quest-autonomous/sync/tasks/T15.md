# T15 - Product Quest controls

## Objective
Connect approved Quest interactions to already-tested shared operations, keeping presentation-only gestures local.

## Shared context and dependencies
T09–T14 drivers/handlers; matrix and prefab-first project rules.

## Scope and preserved contracts
Use existing operations/jobs with local optimistic application. Author controls in the appropriate Quest prefab with serialized references; preserve protocol and domain logic.

## Out of scope
New operation types, alternate domain logic and runtime-created authored UI.

## Automated acceptance criteria
A1. Quest runtime and focused test assemblies compile. A2. Every exposed control reaches its previously tested handler and passes its driver behavior. A3. Local-only gestures do not emit shared mutations; prefab references and invalid-input behavior are verified.

## Verification contract
Static gate, focused Quest PlayMode/EditMode MCP filters after the product control list is fixed; poll jobs and inspect console. Visual control acceptance remains manual.

## Human acceptance
Approve the specific product UI scope and inspect Quest controls in headset.

## Unresolved decisions
UNRESOLVED: the plan deliberately leaves exact product controls open; list and prefab ownership require a product decision before implementation. Focused tests/counts are also open.

## Completion report
Map each control to its existing operation, test and visual result.
