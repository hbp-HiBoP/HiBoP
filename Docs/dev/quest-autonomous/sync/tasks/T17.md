# T17 - Multi-scene lifecycle, selection and global reconciliation choice

## Objective
Multiplex scenes and apply one user reconciliation choice to common incarnations without redesigning the protocol.

## Shared context and dependencies
T16 reconciliation; lifecycle and wire contracts.

## Scope and preserved contracts
Multiple scene/incarnation routing, full-delivery registration, online close with watermarks, per-scene jobs/presentation, last Quest-brain scene/column selection and per-scene choice outcomes.

## Quest interaction context selection — product decision, 7 October 2026

This behavior is explicitly deferred to T17, rather than extending T15's single-scene product-control scope:

The approved [Quest interface and interaction plan](../../quest-controls-ux-plan.md) defines the single-scene controls that this task later extends with shared context selection.

- Starting an intentional Quest brain manipulation selects the corresponding scene and column on both Quest and Desktop. Moving the brain for column 3 of scene B must activate scene B and column 3 on both peers.
- Mere hover, ray targeting, or controller proximity must not change the selected scene or column. Intentional site selection and cut manipulation must resolve their owning scene/column explicitly; the exact integration points are specified with those controls.
- Quest physical brain placement, rotation and scale remain local presentation. Only the selected context is shared, using stable scene/incarnation and column identities.
- Capture the target context when a gesture starts. Subsequent local or remote selection changes must not redirect that gesture to another scene or column. If its target is closed or invalidated, terminate the gesture safely.
- A scene/column information panel is optional and separate from the cut editor. Displaying this context in the cut window is not an acceptance requirement.

Acceptance must include intentional manipulation selecting the matching scene/column on both peers, hover/proximity leaving selection unchanged, and an in-progress gesture retaining its original target across a selection change or terminating on target invalidation. Multi-scene selection must preserve the existing routing, ordering, and echo-suppression contracts.

## Product decisions — 12 October 2026

### Automatic open-scene synchronization

- Add a default-on checkbox to the Desktop Quest connection window, using the nested **Toggle with Text** prefab and existing theme. Persist one Desktop setting common to all headsets.
- While enabled, synchronize the set of open visualizations with Desktop as authority: send all already-open and newly-opened Desktop visualizations, send missing scenes when enabled after connection, and close Quest scenes absent from Desktop. Apply the same policy after reconnection.
- Connected user closes propagate in both directions while enabled. Sequence a Quest close before comparing inventories, so the closed scene is not immediately sent again.
- Disabling the option leaves current scenes open and shared. Subsequent closes are local on either device. A Quest counterpart whose Desktop source closes becomes permanently local/orphaned, including an online close. A scene closed only on Quest remains open on Desktop. Re-enabling restores Desktop's inventory without reattaching an orphan.
- The enabled policy supersedes the earlier orphan-preservation rule: surviving orphans are closed when applying Desktop's inventory. With the option disabled, preserve orphan use and show its broken shared relationship separately from the connected Desktop session.
- The option governs scene membership only. Mutations, selection and visibility continue synchronizing for common live incarnations even when automatic membership synchronization is disabled.

### Open one patient from a multi-patient visualization

- Add a Quest action for the patient of the intentionally selected site. This action is online only, requires a valid common source scene/column/site, and explicitly requests Desktop to open the patient.
- Reuse the existing Desktop single-patient derivation behavior exactly: current configuration and column definitions, single-patient anatomy preferences, corresponding selected column/site, and an independent visualization after opening. Do not introduce persistent parent/child parameter coupling or transfer all patient anatomies in advance.
- Open and share the resulting scene on both devices even when automatic membership synchronization is disabled. Use one publication path so the explicit request and automatic open event cannot create duplicate scenes/deliveries.
- On both Desktop and Quest, a repeat request for the same source multi-patient opening and patient makes the existing open derived scene visible and selects it; deliver it if absent on Quest. Distinct multi-patient source scenes may each open their own visualization for the same patient.
- Closing the source multi-patient scene does not close its derived single-patient scenes. A closed derived scene may be opened again with a fresh incarnation.
- Reject stale targets and give explicit pending/failure feedback; never resolve the request against a later global selection.
- Preserve column definitions and Desktop anatomy selection preferences, but discard source-topology erasure masks and transient MRI-preview selection when deriving a patient scene. These cannot be applied to a different patient topology; the source scene retains its own masks.

### Display scene list and shared visibility

- Extend the existing Quest Display window with a list of open visualizations, reusing the established Quest window, nested control prefabs and theme.
- Each row shows the name, selection color, scene-specific sharing/operation status, a show/hide control and a close control. No dedicated selection action is added: intentional interaction with a column selects its owning scene as specified above.
- Visibility is shared for common incarnations in both membership modes. Match Desktop scene hiding: hide the entire scene presentation and disable all interaction with it, safely terminate active gestures, retain loaded resources and continue synchronization. Keep the row available to show or close the scene.
- Showing a scene must not replay stale gestures. Hidden or closed targets cannot receive interaction through global selection or stale captures.
- Keep physical pose/rotation/scale local per scene/column, including through reconciliation and visibility changes. Place each newly opened scene in front of the current headset pose, with its columns centered horizontally. Do not move existing scenes or allocate progressively more distant scene slots; overlap between scene groups is acceptable (physical feedback, 12 October 2026).
- Keep a new scene invisible and non-interactive until its initial placement is complete. Hide the scientific source renderers throughout preparation and immediately before camera rendering, including when initialization finishes after LateUpdate.
- Show Desktop loading/progress feedback during automatic and manual publication. Concurrent openings/transfers share the loading presentation until the final operation completes, retaining cancellation controls while a cancelable operation remains active.

## Out of scope

## Implementation and verification — 12 October 2026

Implemented Desktop-authoritative inventory synchronization, scoped replica routing, independent per-scene connection/reconciliation owners, acknowledged close/detach barriers and tombstones. Reconciliation shares one conflict-choice task across common scenes; each scene retains its own outcome. Closing/detaching cancels that incarnation's transport/jobs and awaits preparation/reconciliation cleanup before acknowledging, without blocking another incarnation.

The Desktop and Quest patient action share the existing derivation and one source-opening/patient deduplication path. Explicit patient delivery works with automatic membership synchronization disabled. The Display prefab contains the scene list, themed selection names, visibility/close controls and online patient action; the Desktop connection prefab uses the nested **Toggle with Text**. Required owners/references are serialized in the prefabs. Scene visibility remains on the scientific mutation/checkpoint lane; physical placement remains local.

Reload-requiring preferences changes retire both peers before applying settings, preserve derived openings in the reload plan and keep failed openings for the connection window's **Retry** action. Delivery failures and reconciliation failures use their respective retry paths; retrying reconciliation does not overwrite retained offline changes with a fresh full delivery.

## Preference changes requiring scene reload

Desktop remains authoritative for preferences. Reload-requiring normalization changes use this per-scene cycle:

1. Identify all incarnations affected by a preference change.
2. Close Desktop and Quest incarnations with operation barriers, cancellation and awaited native cleanup.
3. Apply preferences and reload affected Desktop scenes.
4. Deliver each scene fully into a new incarnation.
5. Present per-scene success/failure and retry options.

Reject the operation before mutating, saving or transmitting settings while a shared scene is disconnected, a transfer/reconciliation is pending, or Quest holds a local/orphan scene whose original recordings cannot be reloaded from Desktop. Explain the required reconnect/wait/local-close action. Local Desktop openings and independently derived patient openings participate in the reload.

## Follow-up Desktop acceptance fixes - 12 October 2026

The first initial-visibility correction only restored selection notifications. The Desktop window actually follows `OnChangeVisibleState`, so registration must initialize the window from `scene.IsVisible` instead of unconditionally disabling it. The follow-up exercises the real `Module3DUI.OnAddScene` path with the authored Scene 3D Window prefab, its brain viewport, initial visible/hidden states and subsequent hide/show transitions. Prefab import also exposed a null colormap in the information wrapper's editor validation; skip color-map propagation until the texture is assigned.

Opening an already-loaded patient now explicitly shows/selects it, including when hidden, without creating another child. The native derivation regression covers this hidden-child request. Nine focused PlayMode tests passed together (job `d603f218ebd345e383079db2b2b73b11`), including both Desktop-window cases, patient derivation and loading presenters.

The reported manual-send completion message was an interruption dialog, rather than an exception. The heartbeat could mistake the interval between delivery receipt and initial-barrier acknowledgement for a disconnected scene, dispose its owner and cancel the original send while a replacement owner successfully resumed the received scene. In-flight publications are now excluded from heartbeat-driven scene reconnection. Both reconnection and automatic membership synchronization snapshot idle publications before querying the inventory, then verify that their binding and send task are unchanged before applying the response. This also protects a send that finishes while an older inventory is in flight, without blocking reconnection of unrelated scenes.

The production Desktop/Quest loopback regression reproduced the erroneous reconnection decision before the fix and passes afterward. It covers delayed initial acknowledgement, retained-owner resume, successful original send completion, another disconnected scene remaining eligible, and rejection of stale inventory candidates after a later send, binding replacement or closure. Nine focused EditMode publication/reconnection/multi-scene transport tests passed (job `3c62e663e3934cf7ba963dd7ded508bb`, 11.49 seconds); Unity console contained zero errors. Unexpected delivery failures retain the full exception in the Desktop console in addition to connection status. These changes affect Desktop behavior; the installed Quest build remains usable. Physical retesting of the reported dialog remains necessary.

## Normalization reload thread correction - 12 October 2026

The user validated physical test 10 and the preceding fixes, including the manual-send correction. Test 11 exposed a Desktop `get_transform can only be called from the main thread` exception while saving the current camera views before changing normalization. The loading manager starts its callback on a worker thread. Preferences reload now switches to Unity's main thread before inspecting scenes or saving configurations; reopening and the connection window's retry path also explicitly enter that thread before accessing scenes. Configuration capture is inside the reload's `try/finally`, so a failed capture releases the reload guard and permits another attempt without applying preferences or closing the original scene.

Both defects were reproduced before correction: the worker-entry camera exception and the guard remaining set after an injected capture failure. The two PlayMode regressions now complete a real Desktop-prefab reload, verify that preferences are applied on the main thread after old scenes have retired, preserve camera position/rotation/target, and exercise retry through the actual Desktop loading manager. The synthetic fixture explicitly links its site configurations to the saved model before reopening. The final five-case run also includes both Desktop initial-visibility cases and native patient opening/deduplication (job `e7fa66a7f74d4ae2adbac1a86b76ffd6`, 4.24 seconds); all passed and Unity console contained zero errors. The fix is Desktop-only. Physical test 11 must be repeated; test 12 remains pending.
