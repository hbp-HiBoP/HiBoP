The current loopback test supplies a prepared cut ID directly and therefore does not exercise the real `DesktopSceneCapture.Capture` → `SceneArchive` → Quest `SceneRestoration` path or the exact UI-owned runtime cut object. The streaming capture leaves a zero-byte placeholder `.hbscene`; it does not preserve a ready-to-inspect archive of this transfer. Source inspection shows `CaptureConfiguration()` serializes the cut ID and Quest `LoadConfiguration()` restores it, but this has not been proven for the actual transferred instance.

Before another physical run, add bounded diagnostics or a focused real-capture regression that establishes: (1) the Desktop UI cut is the object registered by the live boundary, (2) the emitted cut ID is present in the captured metadata and restored Quest scene, (3) the `SetCutDefinition` construction and authority admission succeed, and (4) the transport enqueues and Quest receives the operation. Include a clear log for any silent skip or local-value rejection. Then rebuild both Players from one source snapshot and repeat a large position move, plus a separate flip or orientation change. ## Diagnostic follow-up and implementation

A Unity Editor probe loaded the same `Assets/Data/IRM/MNI.nii` used by `Small`. `Volume.GetOrientationVector(Axial, false)` returned `(−0.0, +0.0, 1.0)`; the x component had IEEE-754 bits `80000000`. `Base3DScene.UpdateCutPlane` assigns this native orientation to the runtime cut. On a Desktop position edit, `Cut.Position` raises `DefinitionChanged`, and `V2SceneMutationBoundary.OnCutDefinitionChanged` constructs a complete `SetCutDefinition`. Its v2 value validator rejects negative zero. The boundary caught that `ArgumentException` and returned without publishing. This explains the zero Quest receive events while `SiteColor` remained live.

The corrective implementation converts any zero-valued cut position or normal component to canonical `+0.0` when constructing `SetCutDefinition`. The wire validator remains strict; nonzero values are untouched. This follows the T01 wire contract, which rejects negative zero so that numerically identical values have one binary representation for payload comparison, replay and deduplication. A new EditMode regression with a signed-zero axial normal failed before this change because no mutation was proposed, then passed afterward. The existing Desktop-to-Quest loopback test was also updated to carry a signed-zero normal and passed, including persistent transport and Quest-side application. The `Sync.SceneFocused` EditMode category passed **62/62**; two focused wire-validation tests passed **2/2**. The Unity console reported zero errors after the focused scene run. The subsequent physical results are recorded below.

Fresh Android and Windows Players for that retest are under `.artifacts/m1-cut-signed-zero-fix-20260928`, with hashes and source-file fingerprints in its `manifest.json`. The APK passed the content check and uses the Editor keystore certificate above.
